# Landing Studio

Универсальный конструктор адаптивных лендингов с библиотекой блоков.

## Демо
https://marcostavar24633-cyber.github.io/landing-studio/

## Как пользоваться
1. Откройте демо и нажмите «Настроить сайт».
2. Создайте проект или копию в «Мои проекты».
3. В «Структура страницы» перетаскивайте блоки, используйте ↑/↓, скрывайте, добавляйте, копируйте и удаляйте дополнительные блоки.
4. Настройте тексты, цвета, шрифт, ширину контента, фотографию и SEO-поля.
5. Проверьте режимы «Десктоп / Планшет / Мобильный», запустите проверку страницы и скачайте HTML.

## Библиотека блоков
Основные: первый экран, о компании, услуги, преимущества, этапы, отзывы, галерея, стоимость, FAQ, контакты и форма.
Дополнительные: каталог, сравнение тарифов, команда, сертификаты, партнёры, доставка и оплата, блог, квиз-заготовка, карта, видео, скачивание материала, акция. Дополнительные блоки — редактируемый текстовый каркас; сложные интерактивные сценарии требуют отдельной разработки.

## Сохранение и перенос
Несколько проектов сохраняются локально в браузере. Используйте экспорт/импорт JSON для резервной копии и переноса. Очистка данных сайта в браузере может удалить локальные проекты.

## Ограничения
- Нет серверной базы, аккаунтов, облачной синхронизации и общей панели заявок.
- Форма открывает почтовое приложение или мессенджер при наличии контакта. Хранение заявок, уведомления, CRM и антиспам требуют отдельного backend или сервиса форм.
- Домен и SSL настраиваются отдельно в хостинге.
- Проверка перед публикацией вспомогательная; контакты, ссылки, цены, юридические тексты и согласия нужно проверить вручную.
- Не публикуйте персональные данные клиентов и неподтверждённые отзывы/сертификаты.


## Локальный помощник лендингов

В интерфейсе есть кнопка **«AI-помощник»**. Введи нишу — помощник на основе встроенных сценариев и правил подготовит:
- гипотезу о целевой аудитории и её потребностях;
- позиционирование и базовое предложение;
- структуру продающей страницы;
- визуальное направление;
- подробный промт для дальнейшей генерации или доработки;
- стартовый адаптивный HTML-макет, который можно скачать;
- черновик проекта в формате `LandingStudioProject` через кнопку «Создать проект в редакторе» — при успешном принятии штатным импортом он появится в «Мои проекты».

**Помощник работает без API, ключей, регистрации и серверной функции.** Это не подключённая языковая модель: аудитория и тексты формируются локальными правилами и шаблонами. Результат — стартовая гипотеза, которую нужно проверить и отредактировать. Он не выполняет реальное исследование рынка и не должен придумывать цены, отзывы, сертификаты, гарантии, характеристики или контакты.

Кнопка «Скопировать промт» копирует подробное задание. Кнопка «Скачать готовый лендинг HTML» сохраняет автономный черновик страницы. Для уникальной глубокой генерации текстов и изображений можно передать скопированный промт в выбранную нейросеть отдельно.



Кнопка «Создать проект в редакторе» формирует черновую структуру проекта из выбранной ниши и передаёт JSON в поле импорта. Если браузер или обработчик импорта блокирует программную передачу файла, используйте штатный импорт JSON вручную. Всегда проверяйте и редактируйте гипотезы, тексты, стоимость, характеристики, сроки, контакты и условия до публикации. Помощник не подключён к нейросети и не выполняет исследование рынка.

## Уникальные главные страницы (Unique Design Studio)

В редактор встроен движок [Unique Design Studio](https://github.com/marcostavar24633-cyber/unique-design-studio): Design Brief, Design DNA и одна из 10 архитектур главной страницы вместо одного шаблона.

- **Выбор архитектуры.** При значении «Автоматически по нише» архитектуру выбирает движок по нише и содержимому проекта. Он сверяет её с проектами, которые стоят в «Мои проекты» раньше текущего: соседние сайты не получают одинаковый первый экран. Если выбрать семейство вручную (каталог, журнальная, иммерсивная, сервисная, модульная), движок подбирает точную архитектуру внутри него.
- **Предпросмотр.** По умолчанию страница редактора показывает уникальную главную, собранную движком, — то же, что получит клиент. Она обновляется при изменении полей настроек. Плашка «Уникальная главная · архитектура» внизу и поле «Предпросмотр на странице» переключают на стандартный шаблон редактора и обратно; выбор сохраняется в проекте.
- **Группа «Уникальная главная страница»** в настройках показывает выбранную архитектуру, обоснование, сходство с предыдущими проектами и проверку перед выдачей. Кнопки «Скачать уникальную главную HTML» и «Открыть в новой вкладке» собирают самостоятельную страницу движком. Там же выбираются шрифты: автоматически (системные, а с фирменным стилем — Google Fonts), только Google Fonts с кириллицей или только системные без внешних запросов.
- **Фирменный стиль.** Поле «Фирменный стиль» в той же группе применяет профиль одного из действующих сайтов (Слопай букет, ПЕНКА, РАКОВАРНЯ 73, Photograf, ДомА Тех, Hair, РЕМОНТ, Ровно): цвета, гарнитуры и скругления бренда, снятые из кода его репозитория. Архитектуру первого экрана движок при этом выбирает как обычно. Фирменный стиль перекрывает схему и акцент из раздела «Основное».
- **AI-помощник и локальный помощник** показывают архитектуру UDS в результате. Локальный помощник скачивает страницу, собранную движком, и создаёт проект с палитрой и акцентом из концепции, а не с тёмной схемой и золотом по умолчанию.
- **Цвета по умолчанию.** Тёмная схема и акцент `#c6a879` из настроек по умолчанию не считаются выбором пользователя: движок подбирает палитру под нишу. Если поменять схему или акцент, движок их сохранит.
- Если движок не загрузился, редактор работает как раньше (выбор по ключевым словам).

### Обновление движка

Движок лежит в `vendor/uds-engine.js` (один файл, глобальное имя `window.UDS`). В шапке файла записан коммит UDS, из которого он собран. Чтобы обновить движок, положите рядом репозиторий `unique-design-studio` и выполните:

```bash
node scripts/sync-uds-engine.mjs ../unique-design-studio
node scripts/build-app-chunks.cjs
```

`build-app-chunks.cjs` встраивает движок в приложение (загрузчик пишет HTML через `document.write`, поэтому внешний файл по относительному пути не подходит) и проверяет, что после встраивания в странице ровно один `</body>`. Тесты интеграции: `node --test tests/uds-integration.test.mjs`.

## WEB PROJECT CONTROL CENTER PRO

Центральная панель управления всеми сайтами: `src/control-center.html` + `src/control-center.js`. Собирается в `dist/` командой `bash scripts/build-cloudflare-pages.sh` и публикуется на Cloudflare Pages вместе с функциями `functions/api/*`.

### Реестр проектов

Единый список проектов — `projects.json`. Его читают и панель, и часовой монитор. Чтобы добавить сайт, достаточно одной строки:

```json
{ "repo": "new-site", "name": "NEW SITE", "url": "https://new-site.pages.dev" }
```

`url` и `branch` необязательны. Если `url` не указан, адрес берётся из поля **Website** (homepage) репозитория, а если его нет и включён GitHub Pages — `https://<owner>.github.io/<repo>/`. Проект без адреса показывается как «URL не найден», и проверки сайта для него не выполняются.

### Раздельные статусы: качество и публикация

Каждый workflow GitHub Actions относится к одному из типов (`lib/workflow-status.js`):

| Тип | Признаки в названии или пути | Что означает ошибка |
|---|---|---|
| Публикация | deploy, publish, release, pages | Сайт мог не обновиться — **критично** |
| Качество | quality, test, lint, audit, check, validate, lighthouse, ci, qa | Есть замечания — **требует внимания**, публикацию не блокирует |
| Служебный | monitor, health и всё остальное | В сводный статус не входит |

Качество имеет приоритет при совпадении обоих признаков («Quality checks before deploy» — это качество). Статус берётся по последним запускам основной ветки; если по типу их нет — по последним запускам других веток. Отменённый запуск не считается ошибкой.

Совмещённый workflow, где проверки и публикация идут в одном файле (например, «quality & deploy»), делится на две части по заданиям, а внутри общего задания — по шагам. Упавшая проверка тогда показывается как замечание качества, а публикация — как «Пропущена», а не как ошибка.

Итог по проекту: **Критично** — ошибка публикации, сайт недоступен или найден риск безопасности; **Требует внимания** — не пройдена проверка качества, последняя публикация пропущена или аудит нашёл проблему; **Неполные данные** — нет адреса сайта или его не удалось проверить; **Рабочий статус** — сайт отвечает и публикация успешна (или идёт вне GitHub Actions, например через Vercel).

### Проверки сайтов

Общее ядро — `lib/site-audit.js`. Проверяется главная страница опубликованного сайта:

- **Доступность** — HTTP-статус и время ответа.
- **SEO** — title, description, H1, canonical, viewport, robots, Open Graph, lang, robots.txt, sitemap.xml.
- **Адаптивность** — viewport, медиазапросы, правило для изображений, фиксированные ширины от 1000px, alt.
- **Формы** — наличие способа связи, адрес отправки, обязательные поля, кнопка, согласие, ссылки tel/mailto/мессенджеров.
- **Безопасность** — HTTPS, заголовки безопасности, HTTP-ресурсы на HTTPS-странице, `target=_blank` без `noopener`, строки, похожие на ключи (значения не показываются).

Это статический анализ HTML и CSS: он не заменяет Lighthouse, не открывает страницу в браузере и не отправляет заявки. На GitHub Pages нельзя задать свои HTTP-заголовки, поэтому замечание о заголовках там ожидаемо.

Функции панели: `POST /api/site-audit` (все проверки одного сайта для сводной таблицы), `/api/site-check`, `/api/seo-check`, `/api/responsive-check`, `/api/forms-check`, `/api/security-check`. Они принимают только HTTPS-адреса на `pages.dev`, `github.io`, `vercel.app`, `netlify.app` и свои домены проектов (сейчас — слопайбукет.рф). Новый свой домен добавляется в `ALLOWED_HOST_SUFFIXES` в `lib/site-audit.js` в виде punycode и в `url` проекта в `projects.json`.

### Лимит GitHub API в панели

Панель читает публичные данные GitHub без авторизации, а это 60 запросов в час на IP. Чтобы не упираться в лимит:

- одна проверка тратит 9 запросов (по одному на проект) плюс по одному на каждый совмещённый workflow; метаданные репозиториев кэшируются в браузере на сутки;
- последняя проверка сохраняется в браузере и показывается сразу при открытии; если ей меньше 10 минут, новые запросы не отправляются — обновить можно кнопкой «Проверить все»;
- если лимит всё же исчерпан, статусы CI берутся из сохранённой проверки с пометкой времени, а сайты проверяются заново. В строке состояния видно, сколько запросов осталось и когда лимит обновится.

### Часовой монитор

Workflow `.github/workflows/project-health-monitor.yml` запускает `scripts/project-health-monitor.mjs`:

- каждый час и вручную из вкладки Actions (расписание работает из ветки по умолчанию);
- для каждого проекта из `projects.json` считает качество, публикацию, доступность сайта и четыре аудита;
- публикует сводную таблицу в GitHub Actions Summary и JSON-отчёт `monitor-report` в артефактах запуска;
- создаёт Issues с префиксами `[Публикация]`, `[Качество]`, `[CI]` и `[Сайт]` и закрывает их после исправления;
- завершается ошибкой только при критичных сигналах: ошибка публикации, недоступный сайт, риск безопасности, недоступный репозиторий. Замечания качества и аудита — предупреждения.

Для работы нужны включённые GitHub Actions и разрешение workflow на создание и закрытие Issues (`Settings → Actions → General → Workflow permissions`). Монитор читает публичные репозитории штатным `GITHUB_TOKEN`; секреты и персональные токены в код не добавляются.
